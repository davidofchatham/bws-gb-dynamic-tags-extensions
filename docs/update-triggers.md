# Update triggers

One section per code change that obliges a documentation update, a test run, or both.
**`CLAUDE.md` §Update triggers is the index** — it carries every trigger with the harnesses
to run, and links here for the rules that make those harnesses meaningful. A trigger appears
at full length in exactly one of the two places; this page is never a second index. Where the
index says *see detail* instead of naming a harness, there is no harness to name: the trigger's
verification is a procedure, and this page has it.

Nothing here is optional reading once its trigger fires. A harness name tells you what to
execute; the section tells you what the run does and does not prove, which is usually where
the defect is. Per `CLAUDE.md` §Documentation ownership these sections state a rule's
CONSEQUENCE and point at the enforcing site for its AXIS — where the two disagree, the
enforcing site wins.

Triggers with nothing to say beyond "update that doc" stay inline in the `CLAUDE.md` index
and have no section here.

## Field-discovery change

**Fires on:** Field-discovery change (`includes/rest/field-discovery.php` transforms, `assets/js/field-combo-control.js`, the enqueue/inline block, or a flip of any option to/from `bws-field-combo`)

run `php tools/test/field-discovery-test.php` (pure discovery logic) + `node tools/test/field-combo-control-test.js` (the control's display layer) + `tools/test/field-selector-test-matrix.md` rows against the testbed editor (see [testbed.md](testbed.md)).

**THE JS HARNESS RENDERS THE SHIPPED COMPONENT; IT DOES NOT CALL ITS PRIVATE FUNCTIONS.** The display logic is private to the file's IIFE and stays that way — #94's rule, that a control does not grow a test-shaped seam because a test wants one. It is reached through the two things the file already exposes, `window.bwsFieldComboControl` and the `tagSpecificControls` filter, by rendering against stubbed `wp.element` hooks and reading the option lists out of the returned tree. **What it therefore proves is what an author sees** — which rows appear, in what order, how each reads, what the filters do, which option is selected, and what a pick commits — and what it cannot see is the PHP transforms (`field-discovery-test.php` owns those), the REST round trip, and anything needing a real DOM, all of which stay held by the matrix.

**A HOOK STUB INSTALLED AFTER THE FILE LOADS DOES NOTHING.** The control captures `useState` / `useMemo` / `useEffect` into locals at IIFE time. A harness that stubbed them later would silently exercise the first render only — which, since the envelope arrives on a resolved promise, means an empty field list and a suite that passes on nothing. **The envelope is a SECOND vocabulary channel, not only a field list** (#96): `bws_field_discovery_field_note()` emits the field configuration note as ordered SEGMENTS on each entry, and the chain-step control renders what it is handed — so a note change also runs `node tools/test/slot-fold-repeater-test.js`, and the six cases live in [`docs/editor-controls.md` §Field configuration note](editor-controls.md#field-configuration-note). **Definitions only, never a value read** (V5) is what makes it work in a Pattern with no post in scope; an options-page field takes the NON-bidirectional wording, because ACF resolves bidirectional targets by object type and has no case for options. **A boolean cannot select the sentence** — ACF native accumulates-and-hides on a single-entry post object where ACF Extended replaces-and-discards, so the flavour is carried, and both-enabled takes the native wording

## Page-snapshot instrument or baseline change

**Fires on:** page-snapshot instrument or baseline change — `tools/test/page-snapshots.php`, the committed baseline under `tools/test/snapshots/`, the dependency record `tools/fixtures/core-structures/env-versions.php`, or `verify.php`'s snapshot section

**A clean diff proves rendered output did not move on any fixture page, and nothing else we own can prove that.** The reason is NOT the tag-replacement filter: `wp bws render-tag` and every script under `tools/harvest-replay/` call `GenerateBlocks_Register_Dynamic_Tag::replace_tags()` directly, and that DOES reach `generateblocks_dynamic_tag_replacement`, which is applied inside it. **What a direct call cannot produce is the render AROUND the tag**, and that is the real gap: `$block` arrives as `array()`, so anything keyed on real block markup or GB's block-name gate is unreachable; `--loop-item` fakes only `queryType: 'WP_Query'`, so a TERM or USER query loop cannot be produced at any flag combination; and `the_content` filters, `wptexturize` included, never run. **The loop gap is the load-bearing one** — a tag reading the wrong entity inside a term or user loop cannot be reproduced by any instrument except a served page, which is what makes a page-snapshot diff the only acceptance evidence such a fix can have.

**It is a pin over the fixture PAGES, so it proves nothing about a tag that has no visible block.** That is what makes [testbed.md](testbed.md)'s mandatory-visible-blocks rule load-bearing rather than hygiene: a matrix row that stayed `render-tag`-only sits outside the only instrument that sees the filter layer, and no run reports its absence — the diff is clean because nothing was looked at.

**It does not assert the document HEAD, and that is a deliberate hole.** Roughly a third of each captured page was WordPress's `<head>`, where every co-resident stylesheet `<link>` and generated `<style id>` lives — so activating or deactivating any unrelated plugin on the fixture site re-flowed every baseline at once, in a diff carrying no tag output. Measured 2026-08-28: one plugin toggled off produced 10 of 10 pages failing and 6,787 differing lines under the old rules, and 10 of 10 passing under the new ones. What is still captured is `<title>`, `meta name="description"` and `og:description` — the three head lines a `{{...}}` in a post excerpt renders into — plus any `bws-*` `<style>`. Everything else in the head is gone from the artifact, which the artifact says in its own text. **So a head-only regression is invisible to this instrument**, and no run reports its absence; if our output ever reaches a fourth head line, the whitelist is where that is fixed.

**The ACTIVE SET is recorded, and a change to it is a warning like a version change.** `env-versions.php` carries every plugin running at capture, not only the four it requires, because a co-resident plugin can move rendered output without being a dependency of ours. `verify.php` prints a change in both directions after the version lines. **It never fails the run** — the fixture site is shared, and forbidding an unexpected plugin is not this record's job. Note what the pairing buys: the head rule stops a toggle from moving the baseline, and this makes the toggle visible; neither does the other's job, and before both existed the 2026-08-28 reflow was attributed only by someone going to look at the box.

**It proves stability, never correctness.** Wrong output captured as a baseline diffs clean forever, which is the failure mode of every golden-file instrument. The `*-test-matrix.md` files own what a row SHOULD say; this owns whether it changed. The corollary is a capture rule: capture the baseline BEFORE the change under test, never after — a baseline taken afterwards asserts the new behaviour is the old one.

**A diff is not automatically your regression.** `verify.php` prints the dependency-version comparison first for that reason; read it before reading the hunks. Re-capture and re-record `env-versions.php` in the SAME commit (that file's header owns why), and never commit a partial capture — an unreachable page makes the script write nothing at all, leaving the baseline on disk untouched, and a write that fails partway through is reported as a MIXED set rather than a finished one.

**A fixture-page change is EXPECTED to diff, and it is the one case where re-capturing is the answer rather than a cover-up.** A new visible block group moves page output by design, so the baseline is re-captured in the same commit as the blueprint edit and the reviewer reads the diff as the new rows arriving. If it also shows a page you did not touch, that is the finding.
