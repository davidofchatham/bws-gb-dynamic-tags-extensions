## What the trust model actually is

`user_can_author_dynamic_data()` is not the framework — it is one rule's `user_can` callback inside one.

**`GenerateBlocks_Save_Gate` (`generateblocks/includes/class-save-gate.php`, new in 2.4.0) is the framework.** A single enforcement spine for "this user may not save that content", owning every save entry point (`rest_pre_insert_{post_type}`, `rest_dispatch_request` for autosaves, `wp_insert_post_data`, `wp_insert_attachment_data`) plus a shared no-new-exposure exemption. Rules supply only `id` / `applies` / `user_can` / `message` / `error_code`, optionally `enforced` and `exempt`. Its class doc names partner plugins explicitly: they register directly on `plugins_loaded` or later behind a `class_exists( 'GenerateBlocks_Save_Gate' )` check, and there is deliberately no registration action to miss.

The gate is **not** the security boundary and says so: *"the gate is a convenience/authoring layer, not a security boundary on its own... every rule needs its own authoritative guard at output time."* The authoritative layer for dynamic data is the render-time taint model, recorded in `docs/gb-constraints.md` §Dynamic data is suppressed by POST SOURCE.

**Three consumption surfaces exist, not one.** The predicate (PHP), the save gate (a registry), and `generateBlocksEditor.canAuthorDynamicData` — a localized JS flag (`generateblocks/includes/general.php:302`, alongside `dynamicTagsPreview` at `:299`) that GB's own editor uses to null out its Dynamic Data panel and tag-insert toolbar. This plugin reads none of the three; `git grep generateblocks_user_can_author_dynamic_data` still returns nothing.

## Measurements

Four things were measured rather than reasoned about. They are what the decisions below rest on.

**M1 — GB's save-gate rule already covers our tags, with no work from us.** The `dynamic_data` rule's `applies` is `should_validate_content()`, which is `content contains '{{'` **and** `has_block()` for any block in `GenerateBlocks_Dynamic_Tags::get_allowed_blocks()`. No tag-registry enumeration and no tag-name matching, so every tag we ship is in scope by virtue of riding a GB block. A rule of our own would be a second rule over identical content.

**M2 — `src:site` is NOT at parity with GB Pro 2.7.** Pro's `get_option()` callback (`generateblocks-pro/includes/extend/dynamic-tags/class-register.php`, ~`:303-312`) added a per-user REST gate: `REST_REQUEST && current_user_can( 'edit_posts' ) && ! user_can_author_dynamic_data() && ! is_option_allowed_for_current_user( $key )` returns the fallback. `get_allowed_options_for_current_user()` (~`:438-461`, a **public static**) is the shared allowlist minus `get_acf_option_keys()`, filtered by `generateblocks_dynamic_tags_allowed_options_for_current_user`. Pro's own reasoning, worth keeping: only `edit_posts`+ users reach REST routes that render UNSAVED content, so the gate is scoped to them deliberately, and anonymous REST is left alone because blanking it would break headless parity. Our `bws_site_read_option()` carries the ADR 0001 allowlist and no user axis at all, so an untrusted `edit_posts` user previewing `{{text src:site|key:<acf_options_field>}}` reads a value Pro blanks. The two axes are independent: stricter on WHICH keys buys nothing against WHICH user.

**M3 — an untrusted user can never reach our editor controls.** Read from `generateblocks/dist/blocks/text/index.js`. The dynamic-tag modal's outer gate is `canAuthorDynamicData || foundTags.length`; its inner branch is `!foundTags.length || (canAuthor && (selectedText !== null || …))` → the tag builder, else the found-tags list. Walk both paths for an untrusted user: no tags in content → outer gate false, component returns `null`; tags present → outer passes, inner falls to the else branch **every time**, rendering the message *"Your account can't add or edit dynamic tags, but you can remove existing ones."*, the tag names as plain `<span>` rather than the clickable `Button` a trusted user gets, and a Remove button each. `generateblocks.editor.tagSpecificControls` is applied inside the builder's option-control mapper, on the branch that is unreachable. Both consumers of our field envelope (`field-combo-control.js`, `slot-fold-control.js`) live only there, and the `/fields` REST route is that same control's fallback fetch with no other caller.

**M4 — the field-discovery envelope carries no values.** Each row is `name` / `label` / `type` / `return_format` / `context_hint` / `parent_path` / `repeater_key` / `note`. Pro 2.7's analogous hardening (`get_acf_option_fields_for_current_user()`) keeps option field KEYS and blanks their VALUES, so on the values axis we are already where Pro moved to. What remains is the taxonomy — every ACF field key and human label across the `post` / `term` / `site` kinds, inlined by `wp_add_inline_script` on every `enqueue_block_editor_assets` with no capability check, for a user GB has decided may not author dynamic data at all.

**Not measured, and that is the finding.** `grep -rn "taint\|untrusted_dynamic" tools/` returns nothing. The taint model is documented at length in `gb-constraints.md` §193-224 and pinned nowhere. The previous draft of this file asserted that it "covers our rendered output without our help" — read off GB's source, never run against a `bws_` tag. Per CLAUDE.md's measured-or-pinned rule, that sentence should not have been written that way, and closing that gap is now the first task here.

## Decisions

| # | Decision |
|---|---|
| D1 | Row widened from "consult the predicate" to "consume GB 2.4's trust model at the surfaces GB cannot reach". Three surfaces, one decision axis. |
| D2 | `src:site` gets the per-user REST gate. M2 is a divergence, not parity. |
| D3 | Field discovery gets gated — both the inlined envelope and the REST route. Grounds are M3 (the control is unreachable, so the payload buys that user nothing), not a value leak (M4 says there is none). |
| D4 | **No save-gate rule of our own** (M1). Pin the inherited coverage instead of recording it in prose — the coverage is a predicate in someone else's plugin, which is precisely what rots unobserved. |
| D5 | FW-124 stays independent. Worth noting in both rows: routing user-kind reads through `GenerateBlocks_Meta_Handler` consumes the predicate for free, since the handler calls it at `class-meta-handler.php:47,59,71,83`. |
| D6 | The gate calls Pro's **public static** `get_allowed_options_for_current_user()`, `class_exists`/`method_exists`-guarded, falling back to our own derive (allowlist minus `get_acf_option_keys()`, then `apply_filters( 'generateblocks_dynamic_tags_allowed_options_for_current_user', … )`) on Pro < 2.7. ADR 0001's "re-derive rather than read Pro's private state" was about *private* state; calling a public static is stricter lockstep than re-deriving, which drifts the moment Pro changes what it subtracts. |
| D7 | The gate covers **all three** option-read paths, per ADR 0001's own consequence line ("option reads are option reads regardless of which control triggers them"): `bws_site_resolve_value()` key-mode and `bws_resolve_link_url()`'s site branch, both via `bws_site_read_option()`, **plus** the datetime `'option'` branch in `bws_read_field()`, which does not route through that reader and needs its own touch. |
| D8 | New **ADR 0008** owns the user axis; ADR 0001 keeps the key axis and gains a one-line forward pointer. A user-scope decision buried inside an ADR whose title, body and Correction are all key-scope is unfindable by whoever greps for it. The `@invariant` PHPDoc on `bws_site_read_option()` names both gates and points at both ADRs. |
| D9 | Three pins, all `verify.php` sections on the fixture site: **P1** `should_validate_content()` returns true for real serialized block markup carrying a `bws_` tag (the `applies` conjunct); **P2** a restricted save carrying a `bws_` tag is refused with `WP_Error` (the whole conjunction, the user-access half); **P3** a post stamped with `_generateblocks_untrusted_dynamic_content` renders a `bws_` tag as `''` (the authoritative layer). P1 and P2 are different propositions, not belt-and-braces — GB blocks only on `enforced && applies && ! user_can && ! exempt`, and P1 pins one conjunct. |
| D10 | Untrusted-ness in P2 comes from filtering `generateblocks_user_can_author_dynamic_data` to false, not from a seeded role. The filter is the documented seam. A seeded role drags in the whole fixture trigger — blueprint change, reseed, `verify.php` re-run and a page-snapshot baseline re-capture in one commit — and invites a wrong fixture besides: on single-site WP the Editor role holds `unfiltered_html`, so a seeded "non-admin" must be Author or Contributor or it is trusted anyway. |
| D11 | An untrusted editor page emits `window.bwsFieldEnvelope = {}` — present and empty — so `field-combo-control.js:98` resolves it synchronously and never fires the fallback `apiFetch`, which with the route gated would 403 on every editor load. This reuses a shape the matrix already pins (field-selector M8.1, the JSON-encode-failure emission). **No `bws_` escape-hatch filter**: GB's predicate is already filterable, and a second hatch is a second axis on one decision. |
| D12 | A gated read returns `''`, reusing the existing allowlist-miss return. Parity with Pro by construction (Pro returns `''` into `Callbacks::output()`, so the tag's `default` applies) and no new branch in a reader that already has one. |
| D13 | GB facts to `docs/gb-constraints.md` (a new section beside §Dynamic data is suppressed by POST SOURCE, covering the gate, its rule registry and the `canAuthorDynamicData` flag); our three responses to `docs/tag-reference.md`. Name the trap in the GB section: the rule registry is a hook with no action, so nothing fires and nothing fails if a future maintainer assumes we participate. |
| D14 | New update-trigger row, "GB trust-model consumption change", **with** a rules section in `docs/update-triggers.md`. The section earns itself: these pins measure GB's behavior, not ours, so a red pin means "GB moved" at least as often as "you broke it", and the correct first response is to read GB's diff — not to change our code until the pin goes green, which on this surface is how a gate gets quietly removed. Riding the existing field-discovery row was rejected: it would hide a cross-cutting trust decision from whoever edits `bws_site_read_option()`. |
| D15 | CHANGELOG under **Security**, not Fixed — nothing was broken; we diverged from an upstream tightening, and "fix" implies a vulnerability we did not have. |
| D16 | FW-125 closes on ship. **One** new FW row: an untrusted-user fixture, carrying the blank-reason surface (telling an author *why* a preview blanked) in its Open column. Both leftovers are gated on the same missing thing — a real non-admin user in the blueprint — so one row, not two. |

## Seam decisions (added 2026-09-05, second grilling pass)

A prefactor the first pass missed: four call sites would each have written their own guarded "ask GB whether this user is trusted", and two of those would additionally have written their own Pro-version probe for the carve-out. That is one axis written four times, in a repo whose CLAUDE.md owns an axis once. The seam lands **before** either gate. Two boundary seams of this exact shape already exist and set the pattern — `includes/helpers/gb-output-boundary.php` (a file that owns one crossing into GB, with a census harness) and `bws_meta_handler_read()` (a `class_exists`-guarded wrapper with a fallback).

| # | Decision |
|---|---|
| D17 | **Two functions, not one.** The predicate ("may this user author dynamic data") has four callers; the option-key carve-out ("may this user disclose *this key*") has two and is meaningless without a key. Different questions, different fallbacks — the predicate falls back to GB's own default, the carve-out to our derive. One function taking an optional key would force the two keyless callers to pass a meaningless argument. |
| D18 | **New file `includes/helpers/gb-trust-boundary.php`**, sibling to `gb-output-boundary.php`, following that file's stated shape: no re-include guard, bare functions beside bare consts, per the convention its own header explains and shares with `slot-fold.php` and `try-slot-arms.php`. Not appended to `gb-output-boundary.php` — output and trust are unrelated crossings that would then share one trigger row and one census. Not into `field-helpers.php`, where the discovery enqueue would never look. |
| D19 | **A census harness, `gb-trust-boundary-test.php`**, modeled on `gb-output-boundary-test.php`: require the real file, then scan every `.php` in the repo and assert nothing outside the boundary names `user_can_author_dynamic_data` or `get_allowed_options_for_current_user`. This is what makes the seam a boundary rather than a convention, and a convention is what the fourth call site ignores. **The census carries a stated exemption for the pins**, which call GB directly on purpose (D9 — a pin routed through our own helper stops measuring GB). The exemption is the valuable half: it says in one place which sites may ask GB themselves, and why. |
| D20 | **No memoization**, and not merely because GB does not memoize either. A per-request cache would defeat P2, which works by filtering the predicate false and then driving a save **in the same request** — a first answer cached before the filter went on makes the pin measure nothing and pass. That is a tripwire failing open, the defect class `replay-vacuity-test.php` exists over. Four `current_user_can()` calls do not buy that risk. |
| D21 | **When GB's own predicate is unreachable** (every `class_exists` / `method_exists` / `function_exists` probe misses — in practice unreachable, since the plugin header declares `Requires Plugins: generateblocks-pro`), the seam returns `apply_filters( 'generateblocks_user_can_author_dynamic_data', current_user_can( 'unfiltered_html' ) || current_user_can( 'manage_options' ) )` — GB's own documented default, restated at the one site entitled to restate it, which is exactly what Pro does at `class-register.php:374`. Fail-closed was rejected: with GB absent nothing of ours renders anyway, so `false` buys no safety and would blank an admin's editor the moment an upstream probe target is renamed. Fail-open was rejected for hard-coding "no gate" into the branch most likely to be reached by that same rename. |
| D22 | **Capability probes, never version comparisons.** `grep -rn version_compare includes/ *.php` returns nothing — the plugin has no version gate anywhere, and CLAUDE.md states capability probing as the policy. So D6's "Pro < 2.7 fallback" is a `method_exists` probe on `get_allowed_options_for_current_user`, and the phrase "Pro < 2.7" in this file describes *when* the probe misses, never *how* it decides. |
| D23 | **No build tickets.** The `/to-tickets` pass produced four slices that were this file's build order restated, plus acceptance criteria — duplication of a home that already exists, for work sized at one sitting. The condition that would flip it, recorded so it can be acted on later: if any slice goes to a fresh-context agent rather than being built in session, publish that slice as `.scratch/dynamic-data-trust/issues/NN-*.md` first, because an agent picking up the discovery gate cold needs M3 restated as an acceptance criterion or it will gate the wrong thing. |

## Rejected, with grounds

- **Registering a save-gate rule of ours.** M1: duplication. The only thing a second rule could add is an `exempt` proving a save safe that GB's shared no-new-exposure exemption rejects, and no such case is known.
- **Leaving the field envelope ungated because it is definitions-only.** True on the values axis (M4) and beside the point on the reachability one (M3).
- **Gating only the `site` kind of the envelope.** The only kind with a Pro precedent, but M3 is kind-agnostic, and a split gate is two rules where one holds.
- **A blanket blank for untrusted `src:site` reads, with no ACF carve-out.** Stricter than Pro in a way an author notices — `blogname` going blank in a contributor's preview is a support ticket, and Pro deliberately kept core options readable.
- **Pinning GB's predicate as a recorded, version-stamped fact instead of calling it.** Fails the same rule the previous draft failed: a recorded fact nobody re-measures reads as agreement forever.
- **A page-snapshot row for P3.** Puts a suppression regression into the instrument whose baseline is re-captured on every fixture change, where it would arrive as a diff someone accepts.
- **Merging with FW-124, or sequencing behind it.** Different axes (read-path routing vs a per-user gate), and FW-124 has its own unsettled question — whether the two list-shaped traversal sites want the handler at all — so ordering a settled decision behind an unsettled one just stalls this row.
- **A per-read reason code for a blanked value (D12's alternative).** Real support cost, wrong owner: the answer is GB's own editor messaging, not a reason code we would then have to surface. Parked in the D16 row's Open column.

## Build order — four commits

**Commit 1 — the pins (P1, P2, P3) and the GB facts they measure.** No shipped behavior changes. Landing these first records the *pre-change* behavior, so all three are green before any gate exists and stay green after, which is what shows the gates did not disturb the layer already covering us. The `gb-constraints.md` GB-facts section (D13 — the save gate, its rule registry, the `canAuthorDynamicData` flag, and the trap that the registry is a hook with no action) lands **here rather than with the gate**, because these pins are what measure it and a fact belongs beside its measurement.

**Commit 2 — the trust boundary (D17-D22).** `includes/helpers/gb-trust-boundary.php` plus `gb-trust-boundary-test.php`'s census, no callers yet, no behavior change. The "GB trust-model consumption change" trigger row and its rules section (D14) land here, naming the pins from commit 1 and the census alongside them.

**Commit 3 — the `src:site` per-user gate.** Both option-read paths through the seam (D7), ADR 0008 + the ADR 0001 pointer + the `@invariant` PHPDoc (D8), the `tag-reference.md` response section, CHANGELOG under Security.

**Commit 4 — the field-discovery gate.** Predicate on the REST `permission_callback`, `window.bwsFieldEnvelope = {}` for untrusted users (D11).

Four rather than one because the blast radii are unrelated — pins and seam touch nothing shipped, `src:site` changes rendered output for a class of user, discovery changes an editor payload — and because a bundled revert of the discovery gate would take the ADR and the pins with it. Commits 3 and 4 are siblings, not a chain: the discovery gate does not need the `src:site` gate to exist. The earlier three-commit order bundled the GB-facts doc and the trigger row into the `src:site` commit, which made it the one commit too large to hold in a single sitting; both moved to where they are measured rather than to where they are consumed.
