## Two test layers

Run the pure harness always; route integration through the testbed.

1. **Pure harnesses** under `tools/test/` — no framework, no autoload; each runs via `php tools/test/<name>.php`, exiting non-zero on failure. it holds position, never behavior), `entry-lifecycle-test.php` (a tag entry's hand-set `lifecycle` held in agreement with how the tag registers with GB, driven through the real registration passes against a capturing registrar stub), `pattern-cache-test.php`, `gb-output-boundary-test.php`, `gb-trust-boundary-test.php`, `replay-verdict-test.php`, `migrate-string-test.php` (the converter's shared rewriter, driven on a string), `converter-ownership-test.php` — that last one requires the real file AND then reads its source, because half of what it holds is a census of the ownership guard's reason enum and the other half is that the predicate stays callable with no WordPress at all); The tags-in-core-blocks (FW-156) harnesses all require the real files: `core-block-tags-test.php` (the enabled set and its filter, the `core_blocks` key through the real `sanitize_settings()`, the GB allowlist hook and the loop-key `init` pass), `core-block-classification-test.php` (the consequences the classification owner answers), `core-block-picker-test.php` (the settings-page row builder, and that the posted checkboxes keep every saved name through the real sanitizer), `button-host-unlinked-test.php` (the button link rule, plus a census that each shell routes its options through it) and `content-inline-strip-test.php` (the inline-only `{{content}}` strip). `core-block-survey-test.php` also reaches OUTSIDE the repo: it loads WordPress's own block parser from `$BWS_WP_CORE_DIR` (else `D:/Resources/WordPress/wordpress`), because a fabricated parser would test our idea of nesting and malformed comments rather than WordPress's, and it FAILS rather than skips when that file is missing.    **Three are not pure, for three different reasons.** `control-order-test.php` runs against no world at all but is the only harness that sees all three registration constructors at once. `page-snapshots.php` needs a SERVED fixture site, which nothing else under `tools/test/` does. `replay-vacuity-test.php` SHELLS OUT to a sibling script (`diff-replays.php`) and reads its exit status, because the property it holds — that no attestation can fail open — is a property of the whole run rather than of any function; the same treatment is unsafe for `replay-tags.php`, which executes a replay on load, and `replay-source-identity-test.php` reads that file's SOURCE for exactly that reason.    **Some run under `node`, not `php`** — `slot-fold-repeater-test.js`, `editor-filter-chain-test.js`, `field-combo-control-test.js`, `slot-fold-picker-seam-test.js`, `editor-preview-context-test.js`, `table-style-control-test.js`, `table-style-preview-test.js`, `core-block-picker-test.js` (pure JS, reach editor-only logic no PHP harness can; `editor-filter-chain-test.js` also shells out to `php` for the `use` read-rule twin, so a missing `php` fails it), and three PHP harnesses that shell out to `node` for a twin-language check (`slot-fold-twin-test.php`, `serialization-order-test.php`, `fold-migration-test.php`), and `table-style-twin-test.php` (the `{{table}}` validators and `head,args` reader against `table-style-grammar.js`, over `table-style-corpus.json`) — a missing `node` FAILS these rather than skipping, since a silent pass would hide exactly the drift each exists to catch. Each file's own header has its mechanism.

   **ONE OF THEM IS A SEAM HARNESS, and it is the only one that loads two shipped editor files together.** `slot-fold-picker-seam-test.js` mounts the real fold control against the real field picker, because its two neighbours each hold one side and pass while the join between them is broken: `slot-fold-repeater-test.js` stubs the picker, `field-combo-control-test.js` hand-builds the context, and neither loads the other's file. That gap was not hypothetical — `fieldContext()` in `slot-fold-control.js` had one call site reached by no test at all, and reverting its 1.21.0 change fails five rows there while the repeater harness stays green. **Reach for this shape when a property lives in the HAND-OFF rather than in either party**; where one file's behavior is the subject, its own harness is still the cheaper place to say so.

2. **WordPress integration — the fixture testbed.** The pure harnesses can't reach anything WP-dependent (ambient context, ACF/meta reads, GB render, the editor React controls). For that there is a seeded WP site on the local **wp-litespeed** OpenLiteSpeed/Docker env, site `testbed`. **Prefer routing integration smoke tests through it over hand-built pages or live-site probes.** The two entrypoints are `bin/wp.sh testbed bws render-tag` (renders against real ambient context — the cheap what-if engine) and `bin/seed.sh testbed core-structures` (reseeds fixture state).

   [`docs/testbed.md`](testbed.md) owns operating it, and reading it is not optional before an integration run. Two layers of staleness sit between an edit and what you read (the page cache, and a bytecode cache that makes front-end mutation testing silently vacuous), the `bin/*.sh` commands live in the ENV repo rather than here, and the **mandatory rule that every new matrix row group is also generated as VISIBLE GB blocks** is stated there.
